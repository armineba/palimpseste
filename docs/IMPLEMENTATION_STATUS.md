# État de réalisation et point de reprise

Mis à jour le 20 septembre 2026 après la première boucle joueur réelle et l'incident d'un nouveau dessin conservé localement. Les observations de builds, ZIP et sondes antérieurs restent historiques lorsqu'elles sont datées comme telles ; l'état courant est celui ci-dessous.

Preuve détaillée du cas actuel : [parcours joueur, build et relecture sans API](../evidence/public/unity/owner-player-end-to-end-2026-09-20.md).

**Boucle observée.** Un dessin rouge-brun courbe capturé dans le Player a produit un job `production` `ready`. La base indique deux tentatives fournisseur réussies, une description A, un plan B et un `compiled_spell`, sans échec. Le Player a affiché « Faisceau courbe de lave », téléchargé et vérifié la fiche, ouvert le laboratoire et compté un lancement (`Lancers : 1`, `Dégâts : 0`). La génération a utilisé le worker `PalRuntimeSvc` et `codex exec` avec `gpt-5.6-luna` et `max` rapportés. Le trait droit de calibration A `1.3` est un autre dessin : son B `1.1` repris sur la géométrie réelle et ses tests isolés restent des preuves de mise au point, distinctes de ce paquet joueur.

**Build et relecture locale.** Unity 6000.3.24f1 a terminé avec le code 0 le build Windows IL2CPP/URP `game/Build/WindowsPlayerBeamVisibleReady/` : 29 fichiers, 122 093 149 octets, EXE SHA-256 `049F79454586F2AC5445F26B55191CF6611BE62F10C4A5E12F92F806050149C2`, `GameAssembly.dll` SHA-256 `9FB651D09680CAF09B0A8668BEF2A914EFDE6B61F930EDBAE1CE90AF3B5C18C9`. Le paquet joueur a passé 2/2 tests PlayMode du correctif de visibilité à 0,6 s. Une capture du nouveau Player montre l'effet visible puis disparu. Après arrêt de l'API PID `25848`, le Player a été relancé sous PID `35804` : bibliothèque, fiche, laboratoire et lancement du même sort ont fonctionné sans API. L'API a été redémarrée sous PID `16420` et `/health/ready` répond 200 ; le worker PID `8180` est resté actif. Cet essai couvre l'indisponibilité de l'API, sans évaluation humaine du son.

**Nouvelle capture en attente et build correctif.** Le Player PID `35804`, démarré pendant l'indisponibilité de l'API, a conservé le nouveau tracé fermé en `capture_pending` avec `needs_begin=true`, `needs_capture=true` et 151 entrées de journal. Lorsque l'API répondait de nouveau 200 et le worker était actif, aucun nouveau job n'existait pour cette capture ; aucune lecture Luna de ce second dessin n'a commencé. Le code ajoute « Reconnecter » pour rétablir la session puis rouvrir le même parchemin. Unity a produit `game/Build/WindowsPlayerReconnectPlayable/` (29 fichiers, 122 095 741 octets ; EXE SHA-256 `049F79454586F2AC5445F26B55191CF6611BE62F10C4A5E12F92F806050149C2`, GameAssembly SHA-256 `E379AD0EC9CB79533E319BDEB97826E480BE55D614697A66F4183AB81669D75F`). Le journal Unity contient `PALIMPSESTE_BUILD_OK` et « Application will terminate with return code 0 », sans erreur `CS`; le code de retour PowerShell parent n'a pas été capturé. Les 29 hashes du dossier jouable égalent ceux du build brut, hors deux dossiers `DoNotShip`. **Le nouveau Player et la reprise de cette capture n'ont pas encore été exécutés ou validés.** Voir la [preuve de l'incident et du correctif](../evidence/public/unity/player-reconnect-pending-capture-2026-09-20.md).

**Sécurité et limites.** Le worker installé a pour SHA-256 `9243F9600973B1AAF5F97F07AD0983FF60A7EFA2EB0A7F7D42D142C05015847D` et son script enfant `03CE0108D67A4AC27B332A41F36F1F12B2B362FA9A2AEBCF25EB21E8BDB4C104`. Le Doctor installé SHA-256 `AAAAB2686CD9A33ADB6130B205D10596A63AF8207CBAE580ACD723C862196811` a passé son diagnostic local après correctif BOM, sans appel modèle ni `production_issues`. Le manifeste composite v2 SHA-256 `56F349016A5B63D352DD37225AF9253889D496C2399F58F97F70D0DAAC353E3F` lie les appels réels A/B et leur validation/compilation sur les octets d'origine ; `PALIMPSESTE_EFFORT_VERIFIED=true`. Les originaux A/B/encre restent nécessaires et protégés. Les migrations 003 à 006 sont appliquées ; la génération et les secrets restent dans le compte de service isolé, hors du Player et du dépôt.

**Portes humaines.** L'auteur avait rejeté la première lecture « faisceau de feu visuel » du trait de calibration et précisé « laser unidirectionnel de lave ». Aucun verdict positif n'est encore enregistré sur A `1.3`, sur le dessin courbe produit, sur la qualité visuelle, ni sur le son. Les 30 dessins inédits, le second créateur et la machine Windows propre de M7 ne sont pas réalisés. Le laboratoire reste local au propriétaire ; l'usage d'un abonnement individuel commun pour des joueurs externes et les réglages de recharge du compte demandent une vérification distincte. Aucune URL HTTPS publique n'est déployée. Les refus `blocked by policy` avant exécution ont concerné la première commande de lancement de l'API, la création du ZIP et une commande de confort pour fermer puis relancer le Player après restauration de l'API. Le lanceur sûr a résolu le démarrage API ; le dossier Windows exécutable constitue la livraison actuelle sans nouveau ZIP. Le Player PID `35804` est resté ouvert dans sa session issue de l'essai sans API ; aucune relance avec API restaurée n'est revendiquée.

## Échelle employée

`prévu` = aucune source livrée ; `implémenté` = source écrite ; `compilé` = outil de compilation exécuté avec succès ; `testé auto` = essai automatisé exécuté ; `Luna réel` = appels A/B observés avec les images et le compte de service ; `Unity exécuté` = scène et build lancés ; `accepté humainement` = verdict enregistré par un créateur. Un statut supérieur n'est jamais inféré d'un statut inférieur.

## Environnement observé

- SDK .NET 10.0.401, PostgreSQL 17 et Unity 6000.3.24f1 avec module Windows IL2CPP observés. Unity Personal était active. Les builds et tests historiques sont consignés dans `docs/UNITY_TEST_PROOF.md` et `evidence/`.
- Codex CLI patché `0.154.0-alpha.6.2`, compte ChatGPT dédié à `PalRuntimeSvc`, `CODEX_HOME` isolé. Le diagnostic local observe les fonctions d'exécution du modèle désactivées et les refus d'accès à la source ; `unified_exec` demeure un mécanisme interne du CLI. La preuve d'effort composite v2 est approuvée techniquement ; les verdicts de fidélité ne le sont pas.
- L'API locale `127.0.0.1:18080` répondait 200 lors du diagnostic du second dessin, et le worker était actif ; le Player `WindowsPlayerBeamVisibleReady` PID `35804` avait été lancé sans API. Le second dessin est resté local sans nouveau job. `WindowsPlayerReconnectPlayable` est construit mais son lancement reste à vérifier. Aucun endpoint public n'est ouvert.
- Le coffre Windows du Player protège le jeton client sur ce compte ; le coffre de base et les identifiants du service restent hors du dépôt. L'autre compte Windows, l'autre poste et l'exposition multi-joueurs ne sont pas testés.
- Les essais de sécurité, quota et reprise de base sont documentés ; une panne fournisseur ou PostgreSQL réelle pendant un nouveau job reste à éprouver. Les anciens ZIP et mesures d'endurance portent sur des builds précédents.

## Jalons et point de reprise technique

Aucun jalon n'est marqué `accepté humainement`. M0 à M6 disposent des couches techniques indiquées dans la matrice ; les tests de panne et de couverture exhaustive restent partiels. M7 dispose désormais d'une boucle privée **exécutée** sur un dessin joueur, avec build Windows et relecture après arrêt de l'API, mais la recette finale reste ouverte.

| Jalon | Réalisation technique observée | Porte encore ouverte |
|---|---|---|
| M0 | Dépôt, contrats, API health et build Unity réels | Arbitrages P01–P10 et périmètre à valider humainement |
| M1 | Dessin, raster, journal et capture réseau réels ; job propriétaire traité | Essai humain de l'engagement et panne brutale du lecteur |
| M2 | A multimodal réel publié pour le job joueur et affiché dans le Player | Verdict de fidélité sur A de calibration et sur la capture courbe |
| M3 | Géométrie, B, compilation et publication du paquet joueur réels | Comparaison humaine des clauses et règles sur corpus plus large |
| M4 | Six porteurs et effets principaux testés en PlayMode antérieur ; faisceau joueur lancé | Scénarios physiques exhaustifs et jugement humain |
| M5 | Rendu du paquet joueur PlayMode 2/2, build BeamVisibleReady, effet visible puis disparu ; audio technique antérieur | Écoute humaine du son, paires de dessins et reconnaissance visuelle |
| M6 | Service isolé, preuve composite, reprise DB, sauvegarde et cache ; même sort relu et lancé sans API | Pannes fournisseur/DB réelles, autre compte/poste et revue d'isolation plus large |
| M7 | Boucle privée dessin → Luna A/B → compilation → Player → relecture sans API exécutée | 30 dessins inédits, second créateur, machine propre, verdicts humains signés ; M7 non accepté |

**Reprendre ici.** Lancer `WindowsPlayerReconnectPlayable` avec le même profil Windows, ouvrir le second dessin local conservé, essayer « Reconnecter », puis « Transmettre » si ce bouton apparaît ; vérifier la création d'un nouveau job et la publication de A avant toute affirmation de réussite. Si la reprise échoue, conserver le journal et relever le message exact ; l'utilisateur accepte de redessiner. Conserver le premier job `ready` et son paquet téléchargé sans le relancer pour obtenir une autre lecture. Faire écouter le son et recueillir les verdicts des créateurs. Puis mener la recette inédite et les tests sur une autre machine. Inspecter les traces durables avant toute reprise d'une tentative fournisseur incertaine : Codex peut avoir consommé du quota sans réponse publiée. Garder `auth.json`, les rapports privés, la base et les identifiants hors du dépôt. Le worker lit `DATABASE_URL` depuis le coffre privé sous le compte de service. Ne pas ouvrir à plusieurs joueurs avant clarification du droit d'usage de l'abonnement individuel et des réglages de recharge.

Tests récents observés : validation/compilation hors ligne de la calibration par Doctor sans appel modèle ; sécurité du vérificateur composite réussie sur cas synthétiques ; premier job joueur A/B `success` 2/2 et `ready` ; paquet joueur PlayMode 2/2 ; build Unity BeamVisibleReady code 0 ; capture Player effet visible puis disparu ; relance et lancement du même sort sans API ; API redémarrée et `/health/ready` 200. Pour le second dessin, seul l'état local en attente et l'absence de job ont été observés ; le build correctif affiche la réussite dans le journal Unity, sans essai du nouveau Player. Les tests antérieurs (.NET Release, QA 61/61, smoke DB/API, EditMode, PlayMode et endurance) sont documentés dans les preuves de leurs builds respectifs, sans être attribués au nouveau Player.
