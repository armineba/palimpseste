# Plafond serveur de nouvelles générations

L'API admet au plus **3 nouveaux jobs par principal** et **12 nouveaux jobs au total** sur une fenêtre glissante de 24 heures. Les valeurs sont configurables au démarrage par `PALIMPSESTE_GENERATIONS_PER_PRINCIPAL_24H` et `PALIMPSESTE_GENERATIONS_GLOBAL_24H` (entiers de 0 à 10000). Une valeur de 0 ferme les nouvelles admissions. Une valeur invalide fait échouer le démarrage. Les valeurs par défaut sont conservatrices et doivent être choisies par l'exploitant selon la capacité du service.

Les deux points de création de jobs, capture de dessin et diagnostic de plan par créateur, utilisent le même contrôle. Une transaction PostgreSQL en isolation `READ COMMITTED` explicite prend un verrou consultatif commun, compte les jobs déjà créés dans les dernières 24 heures, puis insère le job avant de relâcher le verrou par commit. Plusieurs processus API partageant la même base ne peuvent donc pas franchir simultanément le plafond par une rafale. Le rejet HTTP 429 `generation_quota_exceeded` survient avant l'écriture des nouveaux artefacts. Le contrôle compte les jobs admis, quels que soient leur état ou leur succès ; les jobs d'avant l'activation dans la fenêtre sont également comptés. Le verrou reste tenu pendant la persistance des artefacts : une capture lente peut retarder les autres admissions.

Un rejeu idempotent d'une capture déjà soumise renvoie le job existant avant le contrôle ; reprendre ou réessayer ce job ne crée pas de nouveau job et ne consomme pas une nouvelle admission. La migration `backend/migrations/004_generation_quota.sql` ajoute l'index de lecture pour cette fenêtre ; l'appliquer à chaque base déployée avant de publier cette version de l'API.

Ce plafond **n'est pas une limite de crédits OpenAI**. Un même job peut entraîner plusieurs tentatives du fournisseur, et les appels à Codex hors de cette API ne sont pas comptés. Le plafond borne le nombre de nouvelles demandes de génération acceptées par cette application, sans garantie monétaire absolue. L'opérateur doit garder des contrôles de compte et de supervision séparés.

## Vérification du 20 septembre 2026

`dotnet build Palimpseste.sln -c Release -v:q` et `dotnet build tests/Palimpseste.Api.GenerationQuota/Palimpseste.Api.GenerationQuota.csproj -c Release -v:q` : succès, 0 avertissement et 0 erreur chacun. Le test utilise exclusivement la base locale `palimpseste_test` et crée puis supprime un schéma aléatoire isolé. Vingt admissions concurrentes avec plafonds de test 2/principal et 3/global ont produit exactement 3 jobs engagés ; aucun principal n'a dépassé 2. Un job vieux de 25 heures et une transaction annulée n'ont pas consommé de place ; un principal a été refusé par le plafond individuel et un autre par le plafond global. La sortie publique est sous `evidence/public/backend/generation-quota-2026-09-20.md`.

Le test vérifie la transaction et la concurrence réelles en PostgreSQL. Sa table isolée ne teste pas l'index de la migration 004 ; la présence de cet index a été contrôlée séparément dans `palimpseste_lab` après application. Il ne vérifie pas une requête HTTP complète : le lancement de l'API privée de test avait été refusé par la revue automatique avant exécution. Les chemins idempotents ont été revus dans le code, sans essai HTTP après cette modification.
