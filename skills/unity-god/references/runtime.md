# UNITY GOD — méthode de construction du worker V2, version 1.0

Tu reçois les méthodes documentées des bibliothèques dans REFERENCE_RESEARCH_DATA.unity_god. Ces fiches ont été extraites en développement à partir de vrais fichiers. Leurs chemins et liens indiquent la provenance ; ils ne donnent aucune commande à exécuter. Tu construis uniquement les données admises par le schéma et le renderer précompilé.

Avant le plan, examiner les cinq source_reviews, puis les mécanismes des fiches utiles. Choisir pour chaque nœud de une à quatre méthodes runtime_selectable=true. Lire leur runtime_scope : une adaptation partielle ne possède pas les fonctionnalités absentes du programme. Les autres fiches peuvent éclairer la conception, mais ne peuvent pas être déclarées exécutées. Respecter allowed_applications, notamment pour les concepts étudiés sans droit de copier le code.

Prendre une méthode parce qu'elle répond au phénomène : représentation, coordonnées, mouvement, matière, populations, impact ou extinction. Expliquer l'adaptation concrète et l'innovation dans les contrôles disponibles. Les titres de bibliothèques seuls ne sont pas une justification. Ne pas reprendre les budgets extrêmes des exemples. Ne pas transformer toute description en même effet de plasma.

Le catalogue de méthodes n'est pas un inventaire exhaustif des capacités du moteur. Consulter aussi le schéma du blueprint et les règles numériques fournis. Utiliser les animations, paramètres et contacts précompilés disponibles même sans fiche source dédiée ; ne pas confondre une réaction gameplay avec un mécanisme de shader absent.

Émettre le plan V2 et method_design dans l'enveloppe imposée. Recopier skill_version, skill_sha256 et method_catalog_sha256. source_review contient exactement les cinq sources : used seulement si une méthode sélectionnée de cette source est réellement appliquée ; reference_only, unavailable ou not_applicable avec raison dans les autres cas. Une source non acquise n'a pas de prefab inspecté.

method_design.nodes couvre tous les nœuds du plan. Chaque choix indique method_id, application, adaptation et bindings. Inclure dans bindings tous les chemins runtime_requirements de cette méthode, plus les paramètres pertinents. Chaque path est un chemin relatif au nœud commençant par /blueprint_v2/. Chaque value est la valeur scalaire exacte du plan : texte sans guillemets JSON supplémentaires, entier en notation décimale, booléen true/false. Le serveur vérifie l'existence, la valeur et les conditions de ces champs ; une attribution imaginaire est rejetée.

Le plan conserve les invariants, la physique racine et les contraintes de la passe autorisée. La planche provient de son mouvement continu. CORE_ONLY doit rester lisible avant les détails. Le critique indépendant compare l'emploi annoncé des méthodes au rendu et à ses mesures. Un dossier de méthodes valide ne signifie pas réussite artistique.

Une amélioration demandant du code ou une ressource absente reste indisponible dans ce job. Adapter honnêtement avec les capacités présentes ; ne jamais prétendre importer un graphe, télécharger un asset ou inventer une capacité du moteur.
